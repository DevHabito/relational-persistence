# RP-E004-P01 — preregistered instrument feasibility pilot

**Frozen before any real pilot execution.** This registration is about whether four
distinct software processes can produce internally consistent, independently
logged operational measurements on a single hosted runner. It is **not** an
empirical test or a validation of `C=B/(I*tau)`, nor is it a derived physical law.

## Pilot system, common time and intervention

- A local HTTP service with one bounded FIFO work queue (capacity **512**) and
  one processor initially serving each accepted task in approximately **12 ms**
  (OS scheduling may change actual throughput).
- A *separate* calibration client, load injector, queue-response controller and
  independent health monitor, using four separate process logs and a common
  Linux monotonic nanosecond clock. These processes still share one runner;
  their instruments are **not** independent physical devices.
- The controller checks queue backlog every **25 ms**. If queue depth exceeds
  **5**, it requests a recorded action changing the service's requested work
  interval from 12 ms to **6 ms**. The response event is the **observed,
  successful action request timestamp**, not the nominal policy delay.
- The monitor samples observed backlog every **25 ms**. After independently
  logged injection end, recovery is first observed queue depth **0**
  sustained for **500 ms**. It must confirm this continuous dwell from actual
  samples, not infer recovery from the injected load or controller variables.
- Positive trial: injector submits **120 tasks** spaced by **3 ms** with no
  other planned background traffic. The actual injector log determines delivered
  count and observed duration; configuration is not substituted for measurements.
- Sham trial: injector submits **zero** tasks over the same nominal 360 ms.
  The undefined positive-intervention quotient is **never** assigned a value.
- Calibration: before each trial, submit **120 work units** without controller
  intervention. Record completed-work differences over a **500 ms** window
  after queue saturation is observed. Capacity B is estimated solely from
  this pre-trial completed-work stream, not from observed recovery.
  Calibration must drain to backlog 0 before any trial begins.
- Trials: **2 positive, 1 sham**, order shuffled once with Python RNG seed
  `20261023`. Each trial uses a fresh service instance and logger processes,
  avoiding carryover from a prior controller action.
- Limit per-positive-trial follow-up to **8 seconds** after injection end.
  A non-recovered system is **right-censored**, not discarded. Bound each
  worker, external request timeout and job duration; never contact external
  services from the load generator. No raw external data are involved.

## Measured candidate fields and epistemic status

`B = pretrial_completed_work / calibration_elapsed_seconds`,
`I = successfully_delivered_positive_work / observed_injection_duration_seconds`,
`tau = recorded_controller_action_ns - recorded_injector_onset_ns` in seconds,
`Y = first sustained-recovery_ns - recorded_injector_end_ns` in seconds.

All four timestamps must use the same monotonic clock; missing/zero I or tau
causes the structural gate to reject the scalar as undefined. The recorded
`Y` must not be computed from any of B, I, tau. Use
`src/relational_persistence/measurement_gate.py` unchanged.

The candidate quotient under the selected work-rate convention has units of
**inverse seconds**, not a dimensionless quantity. It is printed solely as
an instrument-schema output, **not** scored against recovery to establish a
persistence law. A controller that changes service speed is a known intervention
mechanism; no novel law can be inferred from queue draining.

## Before-observation decision rule

**PROCEED_TO_SEPARATE_STUDY_DESIGN** only if:
1. All three trials finish with JSON records from separate calibrator,
   injector, controller and monitor processes (each log hashed SHA-256).
2. Both positive trials satisfy the unchanged RP-E003 structural measurement
   gate and include measured positive `B`, `I`, `tau`.
3. Both positive trials recover under the 8-second follow-up with a confirmed
   continuous 500 ms idle interval. Otherwise classify as
   **STOP_INSTRUMENTATION_UNRELIABLE** (right-censor failure reported).
4. The sham has **zero delivered work**; its C is explicitly **undefined**
   and it cannot be counted as a negative positive-dose intervention.
5. All event-log timestamps strictly follow the allowed order; independently
   written logs are traceable with hashes. A failed request, subprocess crash,
   missing event or cross-clock mismatch is reported, not imputed.

The rule above assesses **instrumentation feasibility only**. It includes
no claim about an effect of C on recovery and **no statistical power
assessment**. Three trials are inadequate to support a quantitative
predictive generalization.

## Reproducibility and adversarial checks

Freeze the Python version and runner OS/image information, commit SHA,
actual monotonic-clock resolution and injected-request successes/rejections.
Publish raw event logs (they contain only test-system events) as GitHub Actions
artifacts, plus a small summary JSON; do not store any credentials.

Unit tests must demonstrate that broken event ordering, zero I or tau,
shared logger IDs, non-monotonic time, and censored recovery are rejected or
retained with correct status. They must also verify a common-clock translation
does not alter the derived quantities.

The trial reports actual measurements on a tiny **controlled software
system**, not measurements on naturally occurring physical or social
networks, and cannot independently validate the PMFF or any universal
relational persistence theorem. Observational source-search issue RP-E003
and formal RP-F002 results remain separate.
