# RP-E009-P01 — Prospective transfer to a separately executable TCP/async queue

**Registered before RP-E009 source implementation or new RP-E009 measurements.**

## Question

Does the frozen, unfitted *two-pre-end-sample backlog trend* forecast
from RP-E007 outperform the **static backlog** forecast in a
**separately written, actually executed** queue service whose scheduling
and protocol differ from the earlier HTTP/threaded service?

This study tests **transfer between two software implementations**
using directly observed monotonic timestamps. It is neither an
independent real-world dataset nor validation of a physical law,
and it does not retest the scalar quotient `C=B/(I*tau)`.

## Independent executable and intervention

Create a fresh localhost **TCP JSON-lines** service based on
`asyncio.start_server`, an `asyncio.Queue` FIFO, one async worker,
and real `asyncio.sleep` for each task. Do **not** import the earlier
RP-E004/006 server or its queue/update implementation. A separate
client process drives interventions, queries status, and records raw
events; the service process logs accepted/start/complete actions with
its own process timestamps. The software processes share a host
monotonic-clock domain. The new implementation is operationally
different but is **not** physically independent (both are Python,
same GitHub-hosted cloud platform and a single worker).

The service must complete a pre-intervention calibration of
exactly **60** accepted tasks at pre-change durations cycling through
[8,12,16] ms; `B=60/(last-calibration-completion -
calibration-first-enqueue)` work/s, measured from the client's
monotonic timestamp at first command and the end-of-calibration
status response. Require `B>0`, no unfinished calibration jobs,
and no calibration overlap with the new intervention.
Reset counts while idle and apply **one service-side control
change to double nominal processing rate before the intervention**.
All new work nominal durations cycle through **[4,6,8] ms**.
Record the actual service-applied change timestamp.
This is a controlled change in implementation speed,
**not an experiment identifying causal response latency tau**.

A single fresh server process per trial. Its worker handles every
accepted task exactly once, with FIFO order and an event log that
includes job ID and monotonic accepted/start/complete timestamps.
No cancellations, losses or retries of unaccepted work.

## Frozen study design

Two sequential, newly provisioned GitHub-hosted `ubuntu-24.04`
VM jobs, Python 3.12 and identical source commit and workflow ID:

- 9 **diagnostic** fresh process trials first, never used for tuning;
- 9 **prospective held-out** fresh process trials later, on a
  newly provisioned runner;
- 3 accepted-work targets `N={40,70,100}` crossed with
  3 actual client arrival schedules:
  - `uniform`: 3 ms between accepted tasks throughout;
  - `early_burst`: 1 ms between the first half, then 5 ms;
  - `late_burst`: 5 ms between the first half, then 1 ms.
- The target is a nominal **minimum spacing**, measured actual
  submission timestamps must be retained; do not use the nominal
  spacings in the prediction formulas. The first N/2 rule uses
  floor(N/2); all selected N values are even.
- One run of each cell per block, order fixed by independent seeds
  `20261028` (diagnostic) and `20261029` (held-out).
  No seed selection after seeing outcomes.

Intervention starts at the driver's first enqueue send and ends
when the **last enqueue was acknowledged**. All accepted tasks must
be recorded, with unique sequential IDs and no new work after end.
External health sampling starts before the first enqueue,
approximately every 25 ms, until at least 500 ms after confirmed
idleness. Actual sample timestamps and probe gaps are used.
Reject a gap greater than 150 ms anywhere in the post-end window.

## Frozen target and comparison

Forecast origin is the client-recorded end of injection.
Use **only** the last two service status replies received by
the client at or before that instant, with client-side
`observed_ns` timestamps, `server_snapshot_ns <= observed_ns`,
strict observation times, inter-sample gap <=150 ms,
latest sample age <=150 ms. Each status reports queued,
active (0 or 1), completed and accepted counters.
Their sum `q=queued+active` is the backlog.

Calculate both **unfitted** predictions with the same measured B:

```text
STATIC: yhat_s = q_last/(2*B)
SLOPE:  v=(q_last-q_prev)/(t_last-t_prev)
        q_est=max(0,q_last + v*(injection_end-t_last))
        yhat_t=q_est/(2*B)
```

The unit for B is accepted work/s and all model Y values
are seconds. The outcome is the *first sampled* zero-queue
and zero-active status **after** injection end, confirmed by
500 ms of subsequent sampled idleness. Record and independently
replay the entire sample stream, with no use of either prediction.
This does **not** imply continuous zero backlog between probes.

Audit exact event identities, accepted-start-complete ordering,
strict FIFO service order, proper accepted/complete counts,
no dropped work, valid server timestamps, no samples crossing
the cut-off, and identity of at least two independent
raw-source recovery implementations. A failed/censored/absent
trial or source integrity failure yields `STOP_TRANSFER_AUDIT`
for the **whole** study; no selective exclusion.

## Frozen decision

Primary metric is mean absolute error (MAE, seconds) over
the **9 held-out** observations. The two predictors have
no coefficients fit to data. The 9 diagnostic outcomes
do not alter model form or threshold.

- `PASS_EXECUTABLE_TRANSFER` if valid instrumentation,
  `MAE_static>0`, and `MAE_trend <= 0.90*MAE_static`.
- `NO_REGISTERED_EXECUTABLE_GAIN` if valid data
  do not meet that threshold (including a zero static MAE).
- `STOP_TRANSFER_AUDIT` for any missing, invalid,
  altered, partly timed out, unconfirmed or otherwise
  untrustworthy original record, or failure to reproduce
  a recovery label. Do not convert STOP to NO_GAIN.

Secondary only: per arrival regime and target load MAEs,
9 individual winner/tie/loser indicators, all measured
B and observed injection durations, observed versus
nominal arrival spacing, and train average as a diagnostic
third comparator. No significance test or population
generalization from this sample.

## Reproducibility, archival and independence

Every trial retains the service's raw chronological
event JSONL, complete client health JSONL, separate
calibration and injection JSON with monotonic timestamps,
controller-change JSON, original feature snapshots,
and a source SHA-256 inventory. The independent evaluator
must recompute all original trial metrics and labels
**from raw byte-identical files**, not trust reported
per-trial summary outcomes.

A third GitHub Actions job replays both split artifacts
only after the two acquisition jobs finish. Preserve
the **first** hosted run, its failures and original verdict
permanently on main with a SHA-256 manifest if authorized;
otherwise mark permanent archival incomplete and retain
the original Actions artifacts. Do not rerun to replace
the original attempt, including on failure.

Lean 4 CI is required only as a **regression on existing
formal mathematical claims**. There is no new Lean theorem
and the experiment does not formally verify an actual
OS scheduler, TCP stack or source clock.

## Prior literature and limitations

Asyncio FIFO queues and stream servers are standard
Python primitives:
https://docs.python.org/3/library/asyncio-queue.html
https://docs.python.org/3/library/asyncio-stream.html

Time-aware queue predictions and finite backlog
work-conservation estimates belong to established
queueing literature (see prior-work ledger).
A positive result only supports one separate
executed software implementation in one hosted
environment. It does not imply physical
independence, novel physics or a universal
relational persistence scalar.
