# RP-E011-P01 — Frozen queue-specific historical wait-time prediction

**Status: preregistered BEFORE RP-E011-P01 implementation or any RP-E011-P01 predictions.**

## Exact question and prior evidence

Does a *classical*, unfitted two-snapshot **per-queue waiting-job
count trend** predict independently recorded submit-to-start wait times
at least 10% more accurately than **both** (i) static per-queue
waiting-count/start-rate and (ii) a strong queue/resource-aware
historical completed-wait median, in future chronological observations?

This is a NEW observational benchmark informed by failed E010-P01
(49,995 held-out HPC2N tasks; aggregate trend lost to both classical
controls). The D04 source gate was frozen before D04 code and has
now passed **TEMPORAL_SOURCE_FEASIBLE**, first run #40183836342,
permanent archive `1fef039`. It observed no prediction errors or
wait-time distribution. This source selection and target definition
are nevertheless **not independent blind discovery**: we already
know the first-row ID 0 anomaly from D02/D03, queue count and basic
coverage from D04. All these known facts are disclosed here.

The observable is each job's historical **submission-to-start wait
(seconds)**, not RP-E007/E009 software recovery, not a causal
intervention, not a single FIFO machine, not a validation of
`C=B/(I*tau)`, and not a new theorem.

## Explicit online information boundary

For each target job j at origin `t = submit_j`, only:
- its own queue (extended SWF field 20), requested processors
  (standard field 8), and submit timestamp, all declared
  available at submission;
- the historical event stream of *other* jobs whose original
  submit event is **strictly earlier than** each feature
  snapshot, and whose actual start event occurred strictly
  earlier than that snapshot;
- previously observed waits of jobs **already started** before
  the designated 60-second pre-origin buffer.

Start `s_i = submit_i + wait_i` is reconstructed **offline**
from source, but cannot contribute to any feature until the
actual start event occurs. A job still pending at a snapshot
is counted by arrival minus observed start events at that
instant; its **eventual wait value is not a feature**.
Compare two independent state reconstructions:
(1) per-queue sorted-array binary counts and
(2) a separately implemented chronological start/arrival event
sweep; exact equality at **every** required snapshot is a
mandatory gate. At event-time ties, only events with
timestamp **strictly below** the snapshot are admitted.
No target's current or future wait, actual allocated
processors, runtime, status, eventual end, qsub text, user
ID, node name or test prediction error can enter a
predictor at its origin.

A heldout job may become eligible as **later online history**
once its actual start is strictly earlier than a subsequent
origin's pre-origin buffer. This is **prequential/online
observational evaluation**, not a fixed supervised test with
all heldout labels forever unavailable. This distinction
is declared in advance and applies equally to all predictors.

## Fixed classical, unfitted predictors and controls

For j in queue `Q`, at origin t define snapshots
`u_prev=t-120 s`, `u_last=t-60 s`.
`q_Q(u)` is the number of source jobs in Q with
`submit_i < u` minus the number in Q with
`start_i < u` (both events are known as of u).
No future activity, actual hardware allocation, or
single-FIFO assertion is involved.

Define a history rate over `[t-3600, t-60)`:
`n_Q(t) = # jobs in Q whose actual starts fall in this interval`.
`B_Q(t) = n_Q/3540` started jobs/second if n_Q > 0.

Requested-processor group is fixed:
small `0<p<=2`, medium `2<p<=16`, large `p>16`.
Historical median `H_Q(t)` uses at most the latest 64
jobs that **started strictly before t-60** in Q and
the same requested-processor group, if that group has
**>=16** starts in history. Otherwise, use the
latest 64 already-started jobs in Q (all sizes); if
none, the latest 64 across all queues; if globally
none, return **0 seconds**. Ties in start times
are ordered by positive job ID and use deterministic
ascending ID, then keep the final 64. For even n,
take the arithmetic average of the middle two
(nonnegative) observed waits. All three models
share the exact same causal history, queue, and
fallback rules. This historical median is a strong
resource-aware classical control, not a new
relational-persistence proposal.

The three PRIMARY registered forecasts are:

```
HISTORY = H_Q(t)                                     [control]
STATIC  = q_Q(u_last) * 3540 / n_Q(t)                [control]
TREND   = max(0, 2*q_Q(u_last)-q_Q(u_prev)) *
          3540 / n_Q(t)                             [candidate]
```

For `n_Q(t) = 0`, **both** STATIC and TREND
deterministically fall back to HISTORY (no divide
by zero, no case deletion or imputation from test
outcomes). All three predictions are always finite
and nonnegative. Parameter choices are frozen here:
64 jobs, 16 matching-group minimum, 3600/60/120
seconds, 3540-second rate denominator, two snapshots
and zero coefficients fitted to any target labels.
Any diagnostic exploratory analysis cannot alter
these parameters or retroactively qualify as a
separate confirmation.

This exact TREND formula is **established classical
queue-state extrapolation**, not new mathematics.
This test seeks limited external incremental utility
against stronger per-queue controls, not novelty.

## Frozen scoring, positive and negative outcomes

Score **every** original eligible target in the
169,189-job heldout once, using untrimmed wait
seconds `Y_j=wait_j`. Per job error is
`|forecast - Y_j|`, including all zero and
very long waits. Aggregate unweighted MAE in
seconds; the simple descriptive mean is not a
population-uncertainty estimate because jobs share
queues/time and are correlated.

**`PASS_QUEUE_SPECIFIC_INCREMENT` iff**:
- source/time/duplicate/ID/count/queue/oracle gates
  pass and the exact 169,189 registered heldout
  jobs are scored; and
- `MAE_TREND <= 0.90 * MAE_STATIC` AND
  `MAE_TREND <= 0.90 * MAE_HISTORY`,
  with each control MAE strictly positive.

**`NO_REGISTERED_QUEUE_GAIN`** if every
source and causal gate passes but the joint 10%
advantage fails, including ties, a zero comparator
or even an advantage smaller than 10%.
**`STOP_SOURCE_OR_FEATURE_AUDIT`** for
any source identity failure, oracle mismatch,
causal-feature leak, changed original cohort,
missing target, incorrect split, duplicate ID,
invalid finite quantity, unauthorized exclusion,
or mismatch to the registered model. Never turn
STOP into a passing result.

Report both primary control errors, trend, count
and bias, all 13 queue-subgroup MAEs and original
requested-size groups (no dropped adverse subgroup),
zero-wait count, historical-rate fallback count,
and source/oracle integrity counters.
Queue labels can be recorded in an aggregate
report as SHA-256 hashes of exact queue-name bytes
to avoid unnecessarily republishing identifiable
attributes; full third-party per-job source and
predictions belong in **temporary run artifacts**
only, not the repository. Archive the first-run
summary, provenance, exact SHA256 of original
per-job prediction artifacts and run identity
permanently **even when negative or STOP**.
No retry may replace that first-run verdict.

## Interpretation and prior work

This is one original third-party historical
CERIT-SC grid/VM operational source, not randomized
hardware experimentation. Per-queue labels are
real but no complete scheduling-policy, priority,
cross-queue sharing, stateful resource pool or
truth of a physical scalar is inferred from them.
Shared capacity, changing operating regimes and
right-censoring of jobs without observed starts
remain potential confounders. A PASS does not
establish generality, causality, novel queue
theory or `C=B/(I*tau)`; a negative applies
to this frozen candidate/source/target and is
not an all-domain refutation.
