# RP-E012-D02 — First original Borg production event prefixes: audited

**FIRST preregistered original decision: `SOURCE_PREFIX_AUDITED`.**

For the first time in RP-E012, this source study processed **original
publisher-provided Google Borg production EVENT rows** rather than
just reading the public protobuf SCHEMA. We deliberately examined
only the first 500 complete JSON rows of each of two predetermined
GCS shard files. This is **not random sampling** and cannot support
cluster-wide missingness, performance or scheduling generalizations.

The SHA-256 of the **actual compressed bytes consumed** is:

- Machine prefix:
  `1bd079d9e35f525287cb65995969991ab607b916ec86614653f552cfadaedd47`.
- Instance prefix:
  `5d0ff0b9109ae5c447089b15a4cb618accf9356e52b578ca2956a0af4c5c3ae9`.

Each HTTP response declared a valid partial range
starting at byte 0; one local 16,384-byte streaming
chunk was sufficient to parse 500 complete lines per
file. The server's advertised whole-object MD5/CRC32C
values were recorded as *unverified original metadata*;
they are NOT equivalent to checked full-object hashes
of 16 KiB prefixes. Neither gzip trailer was
read/validated because the prefix sample ended early.

Note that the `instance_events` full first shard
is **465 MB**. Its provider size is not evidence
we downloaded or inspected that entire file.
The hard upper limits allowed at most 2 MiB
compressed per table, 4 MiB decompressed per
table, and 500 parsed complete JSON rows.
In reality, we read significantly less.

## Observed first-prefix event composition

| Measured first-prefix property | Machine events | Instance events |
|---|---:|---:|
| Complete original rows in this audit | 500 | 500 |
| Event code 1: ADD machine | 500 | — |
| Event code 0: SUBMIT instance | — | 495 |
| Event code 8: LOST instance | — | 5 |
| Nonzero missing/reconstructed-event flag | 0 | **5** |
| Missing-type key explicitly present | 0 | 5 |
| CPU/memory resource-request key present | Not part of this table | **500** |
| Machine capacity key explicitly present | **41** | Not part of this table |
| Instance machine-placement key present | Not part of this table | **8** |
| Adjacent strictly decreasing timestamp pairs | **258** | **183** |

These **are not representative estimates of missingness,
priority, resource occupancy or scheduling behavior**.
The file has many other rows and shards, may encode
snapshots as well as events, and can contain
reconstructed/missing lifecycle transitions.
The 495 SUBMIT + 5 LOST count is only an observation
about the fixed first 500 instance records in one shard.

The `capacity` and `machine_id` columns are
optional at the event level. Absence within an
original row is **not** equivalent to zero capacity
or a scheduler without machine placement; event
type determines what may be appropriate.
The observed five nonzero `missing_type` flags
are a useful warning that reconstructed events
cannot be assumed to mark genuine known start
or completion timestamps.

## Timestamp ordering and why this matters

The two original prefix streams are **NOT ordered
monotonically by event timestamp**. Counting each
adjacent strictly descending pair yielded
**258 inversions** for machine events and **183**
for instance events. Both were accepted under the
frozen protocol: event ordering was a descriptive
data-quality property, not a schema failure.

Therefore a future state reconstruction must sort
observed events by timestamp with a formally
declared tie rule and cannot take the first
stored rows as a chronological window.
The original instance shard is particularly large.
A shard-prefix sample is not a chronologically
contiguous subset of the trace. It cannot be
converted to a clean heldout window merely by
assigning a date to its first row.

The observed minimum/maximum timestamps were
0..2,640,239,818,406 microseconds for machine
events and 82,373,323,250..2,669,831,496,698
microseconds for instance events, expressed in
the provider's **relative trace microseconds**.
These are extremes within each prefix, not
the exact original span of all 2019 Borg events.

## Adversarial guards and restricted conclusions

The separately tested strict event-time contract
requires `event_time < origin` for an already
known event, excludes flagged reconstructed
transitions from exact-event assertions, and
forbids using a usage window's end-aggregated
statistics before `window_end < origin`.
No instance-usage raw rows were requested in D02.

Two independent numeric checks verified the
string-encoded decimal time, identity, instance
type and missingness flag values of all 1,000
complete rows; malformed bytes and unknown
event types are STOP conditions, not an
opportunity for favorable selection. The
source-prefix gate passed without a malformed-row
exclusion. No raw IDs or user attributes
were retained in the permanent report.

The fixed outcome `SOURCE_PREFIX_AUDITED`
therefore demonstrates **bounded direct access
to two real original event file prefixes** and
basic consistency of those first 1,000 rows.
It does **not** demonstrate any of the following:

- All historical events for any selected target
  are complete or timely, despite missing-event
  flags and off-order shard streams.
- That a `SCHEDULE` timestamp equals an actual
  operating-system process start.
- That events/data were available online at their
  event timestamps rather than recorded later
  or reconstructed retrospectively.
- That any actual scheduler guarantees the hard
  runtime upper bound required by synthetic
  RP-F007 (E012-D01 found no directly named
  runtime-cap field in the pinned public schema).
- That a regression or predictor beats a known
  baseline in unseen workloads, or that
  `C=B/(I tau)` is measurable or valid.

RP-E010-P01 and RP-E011-P01 remain original
**negative external holdout forecasts**.
RP-F006 and RP-F007 remain **synthetic,
conditional mathematics**, not inferred
physical laws from these rows.

## Next logically isolated gate

A NEW registered D03 source audit could measure
*causal event-reconstruction feasibility* over a
genuinely time-complete original subset, including
cross-shard coverage for machine/instance updates,
missing flags, timestamp ties, resource-request
changes, and distinction between provider
`SCHEDULE` placement and actual runtime start.
It must first establish bounded economical access
to a chronologically coherent portion of ALL
relevant event shards; simply selecting the
earliest 500 file lines is not a valid time
window. Source-driven exceptions must be fixed
in advance and any later exceptions must be
documented as a NEW study rather than rewriting
this first result.

A new **independent forecast** would be a
*separate later experiment* only after that
availability study and with stronger classical
historical/resource controls, independent
heldout dates/cells and no leakage.
