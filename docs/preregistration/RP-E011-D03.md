# RP-E011-D03 — Preregistered source-only localization of the D02 job-ID anomaly

**Status: protocol frozen before D03 implementation, row-level inspection, or D03 acquisition.**
This is a **known-anomaly forensic follow-up**, not a new blind discovery, a
replacement first run, or a revision to RP-E011-D02.

## What was known when this protocol was written

The original RP-E011-D02 result is permanently **DATASET_SCHEMA_REJECTED**.
Its first source run `40148759632` recorded 472,400 rows, 472,400
standard numeric prefixes, 472,399 structurally eligible positive-ID jobs,
13 documented extended queue names, 22 parsed fields on every row, and
**one** nonpositive job ID (under D02's predeclared requirement `job_id > 0`).
There were no duplicate job IDs. The first audit **did not record the
invalid ID's physical line, row ordinal, or value**, and these details
have not been investigated for D03 as of this registration.

D02 was registered at `e3a2d21`, implemented at `a281772`, and archived
unchanged at `b9b0f02`; its source-result reconciliation was merged in
PR #39. The first-run original audit SHA-256 is
`99be405c4e88dfd3646ea1812030eb7927b0a076de808f0257cd55d6e5db11f0`.
None of those records or decisions may be overwritten.

## Narrow question and prespecified alternatives

Can **the same byte-identical original external dataset** independently
reproduce the D02 invalid-ID count, and where is the corresponding record?

- `ANOMALY_LOCALIZED`: acquisition is byte-identical, independent ID
  readers agree for all rows, the full D02 schema profile matches, and
  exactly one nonpositive integer job ID is located. Report its physical
  1-based line number, data-record 1-based ordinal, and exact integer
  value, as well as that line's SHA-256. This is **not** D02 schema approval.
- `SOURCE_ACCESS_BLOCKED`: exact official HTTPS source cannot be obtained
  under the frozen network/size rules.
- `SOURCE_SHA_MISMATCH`: bytes were obtained but the SHA-256 or byte length
  differs. Do not parse these bytes for the registered anomaly result.
- `PARSER_DISAGREEMENT`: either independent reader disagrees on a record
  ID, field width, or record count, or the declared D02 profile cannot be
  reproduced using the byte-identical source.
- `ANOMALY_NOT_REPRODUCED`: both readers agree on the byte-identical source,
  but the nonpositive-ID count is not exactly one. Preserve and report the
  discrepancy without favoring one outcome.
- `INVALID_SOURCE_TEXT`: identical source bytes cannot be read as valid
  UTF-8 and well-formed job lines; preserve the parse failure.

All these outcomes are **diagnostic classifications**, not successes or
failures of a predictive model.

## Independent reading and fixed checks

Use a **new pure-whitespace line reader** and Python `shlex.split` as
independent tokenization methods; for each nonblank, noncomment physical
line, each must extract field 1 as exactly one base-10 signed integer.
Record line ordinal, data ordinal and ID from both and demand equality
over **all** records. The readers must not share one another's token
streams. Independently call the frozen D02 `parse_original` function to
recheck the complete schema counts and 22-field width. Disagreement
between either ID reader or with D02's frozen archive is reported, not
silently reconciled. Counts fixed by the D02 original:
- Exactly 472,400 data rows and numeric-prefix-valid records;
- All 472,400 shlex-parsed widths equal 22;
- Exactly 472,399 D02-eligible jobs, one D02-invalid (nonpositive) ID,
  zero duplicate IDs and 13 nonempty extended queue names.

The new report stores just source provenance, aggregate counts,
anomaly line/ordinal/integer and SHA-256 of the anomalous full line.
**Do not publish full third-party source lines, qsub arguments, user
identifiers, individual waits, queue-level distributions, or bulk data.**
An exact integer job ID in the anomaly record is only a source-record
identifier, not proof of its cause or original administrative meaning.

## No post-hoc redesign

No ID reindexing; no deletion or reinterpretation of the bad row; no
switch from `job_id > 0` to `job_id >= 0`; no D02 threshold changes;
no use of future source contents to change this diagnostic gate; no
forecasting or held-out labels. D03 might identify a `0` or a negative
job ID, but **cannot conclude** whether it was a publisher error or an
acceptable upstream ID convention without separate documented evidence.
Even `ANOMALY_LOCALIZED` leaves D02's **DATASET_SCHEMA_REJECTED**
outcome exactly intact.

Any subsequent observational forecast is a **different** prospectively
frozen protocol, requires explicit and justified row inclusion criteria
and strong queue- and resource-aware classical comparators, and may
not advertise a retrospective fixed D02 `PASS`.
