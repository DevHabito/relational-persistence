# RP-E005-P01 — Prospective two-runner instrumentation replication

**Registered before any RP-E005 hosted trial.** This protocol does not
modify RP-E004-P02's originally registered conditions, source code,
historical measurements, or first-run archive. The project does not
claim that this is a new physical-law experiment.

## Primary question

Can the original RP-E004-P02 **full-probe instrumentation audit**
be reproduced on **two separately provisioned GitHub-hosted Ubuntu
virtual-machine jobs**, with eight fresh software-service trials,
fully preserved per-sample data, and independently replayed recovery?

**Primary outcome:** one binary experiment-level audit decision,
`PASS_TWO_RUNNER_REPLAY` only if all listed gates pass; otherwise
`STOP_REPLICATION_AUDIT`. Do not promote a partial success to a
pass. A run stopped by missing artifacts, corrupted logs, runner
failure, or monitoring gaps is a failure *of the specified
replication gate*, not evidence for or against a physical law.

The two GitHub jobs each execute the unmodified P02 implementation
on a **fresh** service process for each trial. Runner selection is
`ubuntu-24.04` (standard GitHub-hosted VM), Python 3.12, two matrix
slots `runner-a` and `runner-b`; failures in one matrix leg must
not cancel evidence capture from the other. Distinct job slots do
not establish hardware-independent instruments, independent clocks
across jobs, or independent physical systems. Do not subtract
monotonic clocks between jobs.

## Frozen intervention and collection

Each job carries out RP-E004-P02 verbatim:

- Random order fixed by seed `20261024` of two controlled-positive
  120-task interventions, one controller-disabled positive intervention,
  and one zero-load sham, all on localhost.
- 12-ms nominal task service initially, controlled change to 6 ms,
  25-ms nominal controller and health polling, pretrial
  three-window saturated throughput calibration plus sparse probe.
- Separate calibrator, injector, controller and monitor processes;
  service records action under its own state lock.
- Exact roles/log filenames, first observed sampled sustained idle
  of 500 ms after external intervention end, at most 150-ms gaps,
  and at most 8-second follow-up as in *frozen* P02.
- Both enabled positives must provide a measured `B`, `I`,
  actual service application `tau`, and independently replayed
  sampled recovery `Y`. Disabled-positive and sham must continue
  to mark `C` **undefined**, without silently dropping either.
- Each replica archives original `summary.json`, every original
  calibration/controller/injector/monitor JSON, full
  `monitor-samples.jsonl`, `service-actions.jsonl`, and a new
  separate `replica-provenance.json` containing job slot,
  workflow run ID, source commit, Python version, OS family,
  and SHA-256 of the RP-E005 protocol. The P02 log bytes must
  remain unaltered by the RP-E005 runner wrapper.

Original P02 protocol/content hash and all original 24 file hashes
per P02 run are audited **against raw bytes**, not accepted on the
authority of the recorded `summary.json` alone. Recalculate each
P02 trial from the archived bytes with `audit_trial`,
`replay_monitor`, `audit_calibration`, and the existing
`validate_evidence` structural gate. Verify the P02 frozen
preregistration hash. Compare recomputed nested records exactly
against their own run's saved `summary.json` (allow no missing
fields, no imputation, no adjusted timestamps). Reject duplicate
runner slots, conflicting workflow run IDs, incorrectly labeled
interventions or absent traces.

## Frozen decision gates and secondary outputs

Pass if and only if:

1. Exactly two distinct slot artifacts (`runner-a`, `runner-b`)
   belonging to the *same* workflow ID and source commit are present,
   with the expected primary provenance and protocol hashes.
2. Each four-trial P02 run reports `PASS_AUDITABLE_INSTRUMENTATION`,
   exactly its predetermined four trials, and the unmodified P02
   clock/ordering/monitor and calibration gates pass on independent
   replay of all raw events. One bad or missing trial is STOP.
3. Each run has four fresh-service trials, each positive has 120
   accepted tasks, the sham has zero, and only the two controlled
   positives per job define C and Y as prescribed.
4. All **48** role/trace files (six per trial × eight trials)
   are present, nonduplicated by path, and SHA-256 verified
   against the manifest recomputation. Every source byte is
   preserved for review, including failed runs.
5. Every recovered outcome is independently calculated only
   from injector-end and health samples. Only within-run
   monotonic timestamps may be subtracted.

If a host test fails, preserve the failing output as well;
the aggregate reports STOP with reason codes rather than
cherry-picking a replacement run. Later repetitions require
a separately labeled experiment; they cannot overwrite the
first-run evidence.

**Secondary descriptive diagnostics** (no decision threshold,
p-value, fit, or model selection): report `B` in work/s,
`I` in work/s, `tau` in s, `Y` in s and `C` in 1/s
for up to four eligible controlled trials, and the spread of
measurements across jobs. Do not treat two shared-workflow jobs
as an adequate powered independent sample to test predictive
adequacy of `C`; do not compare undefined C controls to
numeric C. Historical P02 output is known at design time,
so this study is not a blinded empirical prediction.

## Archival and reproducibility

Run the first hosted execution only after this immutable protocol
is committed. Use GitHub Actions artifacts to preserve full
bytes *even when the runner trial fails*. The aggregate replay
produces a machine-readable decision plus file SHA-256 inventory.
Attempt a one-time permanent archival commit of the first
observed records to `docs/results/RP-E005-P01-first-run/`
through a source-pinned, trusted main-branch archival step,
only after independently validating the archived event bytes.
If automated archival is not authorized, retain artifact
download links and explicitly classify permanent archival
as **incomplete**. Never invent a successful archival status
or reexecute to reconstruct original bytes.

## Interpretation and limitations

**A passing result is repeatable software instrumentation,
not independent physical replication or evidence for
`C=B/(I*tau)`.** Measurements on GitHub-hosted VMs
share a software model and cloud platform; a fresh VM
does not certify physically disjoint hosts, low sensor
error, causal identification, a general response law or
applicability to nature.

Future *predictive* validation requires a separately frozen
intervention design with true operational variation of
`I` and `tau`, a power/identification analysis, a
classical queueing baseline, independent endpoint labeling,
and held-out trials. It must respect that zero intensity
and absent controller actions leave C undefined.

Prior source: RP-E004-P02, immutable protocol and original
first-run bytes. Methods: standard monotonic clocks,
FIFO queueing, independent event replay and repeated
measurement in systems engineering. GitHub runner docs:
https://docs.github.com/en/actions/concepts/runners/github-hosted-runners

No additional Lean theorem is proposed for an instrument
replication. A successful `lake build` remains a regression
check on the unchanged formal models, not validation of
physical measurement semantics.
