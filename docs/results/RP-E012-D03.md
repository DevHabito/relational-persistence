# RP-E012-D03 — Full original machine-event source audited; joint scheduler state not certified

**First preregistered decision:
`MACHINE_EVENTS_COMPLETE_OBJECT_AUDITED_JOINT_UNCERTIFIED`.**

For the first time in RP-E012, one ENTIRE original Google Borg
2019 event table for cell `a` was downloaded, authenticated
and parsed under registered source boundaries. Exactly **46,219
machine event records**, referring to **10,001 distinct
machine IDs**, were audited, and event-implied state was independently
reconstructed at two predeclared times.

**This is NOT the entire Borg trace, not an original instance
or collection event reconstruction, not a verified online
scheduler state, not a new predictor, and not a physical law.**

## Entire original machine source byte authentication

The original Google anonymous GCS bucket is
`clusterdata_2019_a`, machine table
`machine_events`.

- First page listed **two entries**, but only **ONE matching
  machine_events object**, with NO next-page token. This
  establishes coverage of the matching provider objects
  under the registered original inventory naming rule.
- Single source: `machine_events-000000000000.json.gz`.
- Original pinned object generation:
  `1596844153688368`.
- Exactly **651,854 compressed bytes** were actually
  downloaded, matching provider-reported size,
  with original HTTP **200**.
- The provider's complete original GCS MD5
  `vf+o5W7VQu6rr8+BfU93aw==` was independently
  recomputed and **matched**.
- Original COMPLETE compressed object SHA-256:
  `b04455f48e57c303fc8987b41e35911d89f3aa31e5a6d3997f07e27749dc1791`.

Only the complete machine source was downloaded in D03.

| Conflicting-type same-machine/same-time groups | **0** |

Original minimum timestamp is **0**, maximum
**2,678,851,683,489** microseconds since the
provider's trace origin (not inferred wallclock dates).

The large number of source-order inversions shows that
the event rows are NOT chronologically ordered in
the original file. No inversion was trimmed or
reclassified as corrupt, since the frozen protocol
declared inversion counts DESCRIPTIVE. Events were
reordered by timestamp ONLY for explicitly defined
event-implied state calculations.

The absence of nonzero `missing_type` codes in the
complete machine-events table does NOT imply that
`instance_events`, `collection_events` or online
scheduler machine-state visibility have no missingness.

## Fixed before-origin machine state indicators

Two independent implementations categorized each
originally observed machine ID by its latest event
STRICTLY before the fixed origin. Same-machine
contradictory ties and declared reconstructed
events would have remained separate categories
rather than being resolved by favorable selection.

| Strict origin (microseconds since trace start) | 1,000,000,000,000 | 2,000,000,000,000 |
|---|---:|---:|
| Last original event implies ADD/UPDATE | **9,841** | **9,825** |
| Last original event implies REMOVE | **63** | **121** |
| No event strictly before origin | **97** | **55** |
| Sum across all 10,001 observed IDs | 10,001 | 10,001 |
| Ambiguous same-time conflicting last event | 0 | 0 |
| Uncertain due to most recent missing-event flag | 0 | 0 |

The source records `time` in trace-relative
microseconds. A source event exactly at the
snapshot origin was NOT admitted as prior state.
The two independent state-oracle counts agreed.

These are **event-implied categories**, not measured
live machine availability at those origins.
In particular, they do NOT prove that machine
state changes were available to an operator at
the event timestamp rather than reconstructed
later, nor that all 10,001 machines existed
at the beginning of the trace. An ID with no
earlier event cannot be silently made inactive
or assigned zero capacity.

## Fixed first-page inventories for the OTHER tables

Only the original FIRST 100 provider metadata entries
were allowed for each table; **not one raw collection
or instance event record** was read by D03.

| Original table | Matching shards on first page | Pagination flag | First matching compressed shard, provider-advertised size |
|---|---:|---|---:|
| `collection_events` | 10 | No | 133,462,892 bytes |
| `instance_events` | 50 | **Yes** | 465,101,721 bytes |
| `machine_events` | 1 | No | 651,854 bytes |

Across the FIRST returned metadata page only,
the advertised size sums were
**1,334,163,435 bytes** for the 10 listed
collection shards and **27,398,516,613 bytes**
for the 50 listed instance shards.
Because instance metadata was **paginated**,
50 is **not the total number** of instance shards,
and the 27.4-billion-byte figure is
**not the corpus's overall size**.

The registered 2 MiB full-object machine budget
cannot authenticate the first instance or
collection shard. This is a source feasibility
limit, not a proof that those tables are
intrinsically impossible to analyze under
a different preregistered budget/algorithm.

## What is and is not certified

**Verified:** the publisher's complete named
machine_events table consists of one listed
original object in the current cell-a inventory;
all its bytes were downloaded and verified;
46,219 source rows passed fixed strict event
checks; independent reconstruction from the
same exact machine-only history agreed at
two before-origin timestamps. Original negative
cases (e.g. temporally inverted source-order
events) were preserved.

**Not verified:** completeness or causal release
times of original `instance_events` and
`collection_events`; actual program start times;
join correctness between original machine and
instance events; online resource occupancy;
initial scheduler configuration; machine resource
unit calibration; censoring; or hard enforced
running-walltime caps. Even a complete archived
event file is not a proof of real-time availability.

The first source result **explicitly retains**
`JOINT_CAUSAL_HISTORY_NOT_CERTIFIED`. We did NOT
construct or evaluate a queue predictor, score
a withheld task, refit the existing negative
RP-E010/E011 forecasts, prove a new Lean theorem,
or test a physical `C=B/(I*tau)` relation.

## Subsequent research gate

A future RP-E012-D04 should address **whether
a historically complete, cross-table time window
can be proved to be covered**, with separately
frozen source boundaries, full-shard or independently
verifiable time indexes, treatment of unresolved
missing-event repairs and timestamp ties, and
strictly causal feature construction. The provider's
instance-event shard inventory is paginated
and the first shard is far larger than the
D03 complete-object budget: simply reading
a prefix of each shard will NOT establish
chronological completeness.

No more source download should happen in this
D03 protocol. Future empirical prediction on
Google data must wait for a separately
preregistered coverage/observability gate.
