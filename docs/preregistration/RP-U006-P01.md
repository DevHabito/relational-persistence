# RP-U006-P01 — Executable service recovery after an unavailable-worker intervention

**Protocol frozen 17 November 2026; NO RP-U006 implementation, calibration observation, measurement or result exists at this freeze.** Prior RP-E004/E005/E009 and RP-U005 experimental results are already known. This is a deliberately limited **single-host executable software instrumentation and prediction experiment**. It is not a new result in queueing theory or physical, biological, clinical or ecological resilience.

## Measurement gap following RP-U005

RP-U005 directly contrasted graph structure F1/F2 with an **independently stipulated** service/queue recurrence. A topology restored to two paths did not identify a recovery timestamp without the accumulated backlog. The next step is to replace the exact prespecified queue arithmetic with measured asynchronous service execution, while retaining a separate operational recovery endpoint.

Other studies in this repository have already implemented a localhost HTTP queue, independent role loggers and a TCP/asyncio service (RP-E004/P02, E005, E009); this is **not** the first real executable queue, independent physical instrument or new predictive mechanism. In particular, the present model's `available` control is a software worker-availability gate, **not a measured network edge restoration or two-route topology**. The comparison is therefore fairly named *availability-only* versus *availability plus measured outstanding work*. No `B/(I·tau)` scalar is evaluated.

The question: given a service that has just been re-enabled, does a **pre-response** measurement of the amount of accepted but not yet completed work improve prediction of how long it takes for its entire work queue to remain empty for two consecutive observations, compared with a trained *availability-only* baseline?

## Registered executable and separate measurement roles

Use the standard Python 3.11 library with separate operating-system processes on **one GitHub Ubuntu 24.04 VM**:
- The **service** is an `asyncio` localhost TCP JSON-line server, with exactly one FIFO worker. While its `available` gate is false, that worker cannot dequeue any task. On `enable`, the worker begins serving one task at a time, each with an actual `asyncio.sleep(0.012)` duration. The 12-millisecond request is a **minimum runtime**, not a guaranteed service time. Record each task's accept, start and completion with server-side monotonic-nanosecond stamps and unambiguous integer IDs. No job may disappear, reappear or be completed twice.
- The **injector/controller** in the orchestrator process submits a specified, numbered batch *before* the enable command; there are **no post-enable arrivals** in this pilot. The controller logs actual submission acknowledgments, the server's enable-application timestamp, and a pre-enable `health` snapshot of `accepted-completed` outstanding work; all such feature inputs must be fixed before the target is observed. The number accepted is also known to the injector; therefore the extra backlog observation is a **state/measurement feasibility test**, not evidence of a previously unobservable quantity.
- The **monitor** is a separately spawned process that makes read-only `health` RPC requests approximately every 20 ms, retaining its own read-receipt timestamps as well as the server's source timestamp and queue/active/accepted/completed counts. Its samples cannot change service state. The monitor's readings depend on the service endpoint — **they are not an independent hardware sensor**.
- One fresh server process and one fresh monitor process are required for **every** calibration, diagnostic and holdout trial. The orchestrator must record complete per-trial logs, sidecar configuration, SHA256, process exit observations and timeouts; it must not reuse a previous trial's source file.

No actual physical network link is broken or repaired, no external traffic is measured, and process/OS timing is not deterministic. An elevated error or a time-base discrepancy is a valid negative or invalid-run outcome, not grounds to tune the pipeline on the holdout.

## Fixed order of 15 trials

Each trial starts from zero accepted/completed jobs and an unavailable worker except the calibration trial. Start a fresh service and monitor; submit the entire batch with explicit sequential job IDs; confirm `accepted == N`, `completed == 0`, `queue+active == N`, and that no completion occurred before enabling. Start the monitor and verify initial observations of a nonzero queue for nonzero N. On acknowledgment of `enable` record the **server-side application time** and the controller receipt time; no additional tasks may arrive. Keep monitoring until at least two qualifying zero-outstanding samples, then retain at least 60 additional milliseconds of monitor samples. Gate fail if the service never drains within six seconds, if after-enable samples have a gap over 120 ms, or if any server/client/monitor clock ordering is impossible.

Predeclared order:

1. **Calibration block:** one fresh server enabled immediately (no unavailable period) with 12 work items, using only server-side consecutive completion stamps to obtain `calibrated_service_interval_sec = median(diff(stamps for jobs 4..12))`. Use no holdout data or outcomes to calibrate. Require 9 usable intervals, each positive; if not, mark entire study invalid. For the calibration only, target recovery is not used in the forecast.
2. **Diagnostic/training block:** exactly six separate interventions, workload batches `[8,16,24,8,16,24]` in this order. For each, measure the recovery target. Fit the **availability-only baseline** as the **median of these six diagnostic measured recovery durations**, independent of the holdout jobs' outstanding counts. Freeze that single baseline scalar before any holdout intervention.
3. **Holdout block:** exactly eight fresh interventions, workload batches `[7,11,15,19,23,9,21,13]` in this order. No reselection, random restarts, file replacement, interpolation, model tuning, changed dwell/monitor period or calibration after seeing the first holdout target.

Total **15 trials**, with 14 recovery targets (six training and eight future holdout). The calibration and diagnostic targets are not held-out observations. The cohort is one VM and one software program, not independent human/physical replicates.

## Exact target, estimators, negative controls, and decision

For any intervention trial the service is `available=True` at an authenticated server-side timestamp `t_enable`. The registered functional recovery target is the time (in seconds) from that timestamp to the **second** of two consecutive independently *monitor-recorded* health samples in which `accepted-completed == queue+active == 0`. Both samples must be strictly after `t_enable` and separated by at least 15 milliseconds, with no intervening nonempty sample. This finite sampled endpoint is **not continuous zero backlog**. Distinct role time stamps are on the same Linux monotonic clock but not separately synchronized physical clocks.

The two forecasts are formed **immediately after enable acknowledgment and before observing the recovery target**:
- `forecast_availability_only = median(training recovery seconds)`. This is a fairly trained static comparator for the one common `available=True` condition; it is not forced to zero.
- `forecast_with_state = measured_pre_enable_outstanding * calibrated_service_interval_sec + 0.040` seconds. The 40-ms offset is a registered **monitoring two-sample latency allowance**. No feature uses the future completion count or future monitor endpoint. No coefficients are fitted to diagnostic/holdout targets in this state-aware formula.

On each of the eight fixed holdouts, compute absolute forecast error against the independently monitored target. Primary MAE gate:

`MAE_state <= 0.75 * MAE_availability` **and** `state_abs_error < availability_abs_error` on **at least six of eight** holdout trials. The strict individual win uses raw unrounded timings; ties are not wins. Both conditions must hold for `RP_U006_EXECUTABLE_STATE_FORECAST_GAIN_WITHIN_HOST`. If all 15 valid trials and requirements are met but the gate fails, report `RP_U006_COMPLETE_NO_REGISTERED_GAIN`. Report every individual loss, MAE, trial outcome and timing. **No p-value or out-of-sample population generalization** is claimed for eight deterministic workloads.

One mandatory negative **software-unit** control: accepting zero jobs while the worker is disabled must keep `accepted-completed=0` after enable, so the target should occur within 0.120 seconds with two valid monitor probes; this is a separate **sixteenth** optional? **No**: the zero-job sham is an additional *independent synthetic unit test*, not a 16th original trial, and must be run as a pre-data local in-memory oracle without changing the 15-trial source sequence. It cannot count as a held-out prediction. Explicitly test wrong IDs, duplicate completions, stale snapshots, missing monitor intervals, false early zeros, forged clock ordering, incomplete original files and baseline leakage.

All-in-run invariants: record a separate append-only service-events JSONL with job IDs and monotonic time; injector/controller and monitor data must be source-hashed; independently recount unique accepted and completed IDs from service log after each trial. All original interventions must satisfy `accepted == completed == N` at the end and pre-enable `completed == 0`; monitor `queued+active == accepted-completed` for every probe. Do not condition inclusion on lower prediction error or omit any failed trial. A single missing/invalid trial, time-base failure, audit disagreement or unavailable service yields `RP_U006_MEASUREMENT_INVALID` with all attempts and partial source hashes, and **no confirmed forecast result**.

The first hosted implementation must run source-independent synthetic/adversarial tests before any actual service trial; full repository Python 3.11/3.12 CI must pass. Lean 4 is a **prior proof baseline only**; the experimental timing and OS scheduler are not Lean-verified. The workflow must execute exactly once upon the separate runner commit, with a stable path trigger, then SHA256/archive first `docs/results/RP-U006-P01-first-run/summary.json` and every original source trace as a GitHub Actions artifact. Keep the exact first original source evidence and failures; do not overwrite or relabel a rerun as first.

- The repository's RP-E009 existing asyncio TCP service and acquisition code, and RP-U005 first synthetic result, provide disclosed engineering/context precedents; this experiment is a new intervention on a **different service gate and held-out forecast rule**.

The preregistered study is a **software measurement bridge** from the finite U005 witness. It does not validate the original scalar index, establish brain or ecological persistence, measure real network repair, independent physical recovery, or discover a new law. A subsequent real-world dataset or externally instrumented service would be required for broader claims.
