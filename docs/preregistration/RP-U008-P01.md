# RP-U008-P01 — External network-telemetry recovery concordance at a first-hop outage

**Registered on 17 November 2026 before opening the original raw trace for RP-U008 analysis. The publisher's dataset card, published episode summary, original recorder source code, metadata/config and Git object identities WERE read at study design time. This is not a blinded discovery of four interruptions. No RP-U008 original waveform, numeric row, recovery sequence, computation or outcome has yet been inspected.**

## Why this is a necessary change of evidence level

RP-U007's 12 prospective single-host worker-gate trials yielded NO CONFIRMED INCREMENT from a fresh queue reading when the baseline already knew accepted load and measured service capacity. We should no longer claim that another hosted synthetic queue would establish relational persistence. The next narrower question is whether, in a real externally recorded network, the end of a first-hop connectivity outage and the recovery of an independently probed application endpoint are observable at **the same sampling resolution**.

The publisher is Alexander Ezharjan, *LocalNet-Dynamics: A Longitudinal Local Area Network Telemetry Dataset* (2026), v1.0.0, DOI https://doi.org/10.57967/hf/10841. The public original source is \`Ezharjan/LocalNetDynamicsDataset\`, immutable Git commit \`d57ca705bfd2b0340b6476a2d01553d2c967636e\`, originally recorded from one wired Windows workstation on one residential network. The original UTF-8 CSV is \`dataset/raw/localnet_desktop-eth_20260920_123407.csv\`, Git blob identity \`d3a5a90f1a21125e06f2dbc1047a082f748dac1c\`, exactly **15,143,900 bytes**. The publisher's dataset card is blob \`ee46bb99bb6a60fa549b87179ced62669bb28d47\`. The author's consolidated release declares 54,617 samples at about 30 s from September 20 to October 9, 2026. The original collector measures local gateway ICMP, remote ICMP, TCP, DNS and one actual HTTP GET to \`http://www.msftconnecttest.com/connecttest.txt\`. Its configured remote ping target is \`8.8.8.8\`. Source data come from ONE local machine and ONE software collector, not independent hardware instruments.

**Already disclosed pre-registration knowledge:** the author's published card describes **four** short all-first-hop outages lasting about 2–2.5 minutes, an improvement in loss at the end of September, and multiple long latency episodes. We have seen the card's claims and dates; the prospective aspect is only the **exact below-defined first raw-record extraction and endpoint comparison**, not the discovery that outages occurred. No original CSV row values or lag after recovery were examined before registration.

## Source admission and no substitution

Fetch only the exact pinned raw CSV from the publisher's original Git revision (not a derivative with computed \`label_outage\`) using the exact immutable raw URL. Enforce total body size and publisher Git object SHA1, independently compute original raw SHA256. Never fall back to a fork, a mirror, the consolidated CSV or another version. Require exactly 54,617 data records, no timestamp duplicate, strictly increasing UTC timestamps, expected run_id, and required raw columns \`timestamp_utc\`, \`epoch_s\`, \`run_id\`, \`packets_sent\`, \`packets_received\`, \`packet_loss_pct\`, \`gateway_packet_loss_pct\`, \`gateway_rtt_avg_ms\`, \`http_status\`, \`http_ms\`, \`tcp_connect_median_ms\`, \`dns_resolve_ms\`. Reject out-of-range losses, missing or inconsistent packet-count fields and nonfinite or nonpositive observed HTTP latency. Missing HTTP response is a permitted **negative functional observation**, not an imputed success. No user-identifying raw IP address/notes columns are exported into this repository. Record only bounded per-outage metrics and source digests.

The publication and author's own time-of-collection metadata report one workstation; no externally certified manual event/repair log or \`events.csv\` exists. **Do not call the first returned ping a repaired graph edge, router replacement, proven hardware fault, stable physical causal path or restored service to all users.** It is the first sampled return of ICMP reachability for one vantage point.

## Fixed four-event selection from RAW measurements only

Define a raw candidate DOWN row iff all of these hold:
- \`packets_sent=10\`, \`packets_received=0\`, \`packet_loss_pct=100\`;
- \`gateway_packet_loss_pct=100\`;
- timestamp is valid and unique.

A registered outage is a **maximal contiguous run** of candidate DOWN rows with adjacent sample timestamp gaps no greater than **75 s**, containing **at least 3 observed DOWN rows**. Any shorter isolated DOWN runs must also be reported as excluded under this fixed threshold; do not omit them silently. Require exactly **four** eligible events for a complete four-event description, otherwise \`RP_U008_SOURCE_OR_EVENT_CENSUS_INCOMPLETE\`, not a re-picked sample or positive discovery.

For each of the four in chronological order, save (without raw source notes) start/end timestamps, number of DOWN rows, adjacent timestamp gaps, and exactly five immediately preceding observations and ten immediately following observations when available. Reject local window eligibility if any interval separating the 5 pre, outage, or 10 post observations is greater than 75 s, if another DOWN event starts within the ten-row post window, if event times or run_id mismatch, or if fewer than the required observations are present. No event can be replaced by a fifth event. Report every local-window failure explicitly rather than silently dropping it; an ineligible event blocks any complete primary claim.

## Separate structural proxy, application response and quality endpoints

The first-hop connectivity PROXY is a gateway health row iff \`gateway_packet_loss_pct < 100\` and a finite nonnegative \`gateway_rtt_avg_ms\` exists. This is **reachability**, not necessarily fully restored packet-loss performance.

The distinct application FUNCTIONAL observation is an HTTP-success row iff \`http_status\` is an integer in **[200,399]** and \`http_ms\` is finite and strictly positive. A 4xx/5xx status, missing status/latency or no response is not an application success in this protocol.

The SERVICE-QUALITY observation requires the same valid HTTP response AND \`http_ms <= 1,000\` milliseconds, so slow (potentially retransmitted) responses remain distinguished from successful but degraded transactions. This absolute one-second threshold was fixed with knowledge that the original card describes HTTP retransmission tails; therefore it is **not an undiscovered threshold or a new biomarker**.

A two-sample recovery timestamp for each endpoint is the **second** of two consecutive endpoint-success observations among the first ten post-outage rows, provided the two post rows are no more than 75 seconds apart. Do not use DOWN or pre-outage rows as recovered samples, and do not treat the source's concurrent probe columns as exact, separate operation timestamps. If a qualifying pair does not occur within ten rows, the endpoint is **right-censored** at the post window, not “never recovered.”

Define for each event \`lag_http_bins\` and \`lag_http_quality_bins\` as the integer **row-index distance** between the respective recovery-pair second row and the gateway-pair second row. Positive means HTTP pair was seen later; negative means HTTP pair was seen earlier (possible because the 30s sampling row combines separately scheduled probes and health definitions); zero means **not distinguishable at this source's sampling granularity**. Also record the corresponding source timestamp difference in seconds, but **never claim that it is true network recovery duration**.

Additional descriptive probes (not the primary outcome): whether TCP median connect is finite/positive and cached DNS response is finite/positive on those same rows. These share the collector and may fail independently; they do not certify successful HTTP.

## Frozen decision hierarchy and controls

The **PRIMARY** external observational gate is: all four eligible events, all windows complete, and both the gateway and HTTP success two-sample recovery pairs observed for all four. If any part fails, set \`RP_U008_EXTERNAL_RECOVERY_CENSORED_OR_INCOMPLETE\`. Report every censored event, original counts, missingness, and observations regardless.

If the primary gate is complete, classify a *descriptive reproducibility threshold* \`RP_U008_TWO_OR_MORE_POSITIVE_HTTP_LAGS_OBSERVED\` only when at least **two of four** events have \`lag_http_bins >= 1\`. Otherwise report \`RP_U008_NO_REPEATED_POSITIVE_HTTP_LAG_AT_SOURCE_RESOLUTION\`. These are **not statistical significance results** and do not justify inference outside this one host. The HTTP-quality lag is a separately registered descriptive diagnostic, not a route to retune the primary endpoint. The one-second quality result cannot replace an unavailable basic HTTP result.

Negative controls / falsifiers to preserve:
1. All-four observation census instead of choosing favorable events.
2. Independently recompute the exact DOWN-run selection using an alternative pass over immutable raw rows, match all indexed runs and the first algorithm.
3. No endpoint-positive from missing HTTP status, negative HTTP latency, malformed numbers or failed gateways.
4. A synthetic example with HTTP recovering **earlier** than gateway must yield a negative lag; do not clamp lag to zero.
5. A synthetic example with exactly one later HTTP result fails the repeated-lag threshold.
6. A synthetic example with a missing post window or no two-success pair is censored and blocks a complete primary claim.
7. Original publisher dataset "outage label" and aggregate authors' published episode table are **not permitted** as the selector or as ground truth for either recovery timestamp.

Every synthetic/adversarial test is run and logged **before** the first original source CSV is downloaded on the hosted runner. The first original run must preserve source validation failures, original publisher URL, commit/blob/byte/SHA256 identity, all eligible and excluded run counts and bounded anonymous per-event recovery comparisons. Pin original code commit and workflow ID. Retain the original immutable first-run JSON and its SHA256 in the branch, with a separate report and regression checks. Never overwrite the first result or turn a technical failure into evidence.

## Literature and scientifically responsible interpretation

- Alexander Ezharjan (2026), *LocalNet-Dynamics*, v1.0.0, DOI https://doi.org/10.57967/hf/10841. This study explicitly relies on the author's prior event report, which should be cited and never marketed as our outage discovery.
- CAIDA, *Internet Outage Detection and Analysis*, https://www.caida.org/projects/ioda/. Different instruments/signal types are used to corroborate outages; single-vantage measurements are fallible, and multiple protocol columns in one collector do not constitute independent event ground truth.
- John Heidemann et al., *A preliminary study of network outages*, USC/ISI/ANT datasets, https://ant.isi.edu/datasets/outage/. Outage up/down inference has known sampling and missingness limitations.
- Earlier RP-U005–RP-U007: structural graph-service toy model, then single-host TCP-worker service outcomes. All remain separate; do not retroactively call them real router failures.

An outcome of **zero** repeated lag is as scientifically useful as a positive one: it would show that this trace does not resolve systematic delayed HTTP recovery beyond gateway reachability. **Neither possible outcome demonstrates a new universal law, relational-persistence mechanism, emergent time, disease stabilization, neural self, real physical repair, or cross-domain generalization.** The responsible follow-up would involve independently timestamped network-link and application-level events from different measurement agents, with registered outages and more than four incidents.
