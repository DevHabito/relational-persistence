# RP-E012-D01 — Independent original Borg v3 schema: events yes, hard runtime guarantee unverified

**Original first-run decision: `SCHEMA_EVENT_METADATA_PRESENT_RUNTIME_CAP_UNVERIFIED`.**

This is a verified *external publisher's schema* result, **not a raw
production-event or predictive study**. The v3 schema fields were
inspected manually **before** the new protocol; this was
**informed-source feasibility triage**, not blind discovery.

## Reason for this study

A separate synthetic RP-F007-A01 demonstration established that an
**actually enforced** upper bound on a currently running job's service
duration can reduce its mathematically admissible residual-service
interval. It did **not** demonstrate that real logs contain an
enforced wallclock runtime cap.

Two other original external prediction benchmarks remain negative:
RP-E010-P01 (49,995 HPC2N heldout waits) and RP-E011-P01 (169,189
CERIT-SC heldout waits). We must not retune those already opened
holdouts or treat a schema as a third forecast result.

The next step was to ask what an *independent original* production
schema DOCUMENTS, before downloading and investigating any rows.

## Strict first-run field capabilities

Both independent parsers agreed on all prespecified message fields
and enum values. The source provides **schema-defined potential
inputs** for an event-time reconstruction, not evidence that every
row is present, reliable or historically visible before a target's
decision time:

| Publisher message or enum | Relevant verified names | What can and cannot be inferred |
|---|---|---|
| `InstanceEvent` | `time`, `type`, `collection_id`, `instance_index`, `machine_id`, `resource_request`, `priority`, `missing_type` | Can express timestamped scheduler-instance events, requested resources and priorities; it does NOT itself prove execution actually started at SCHEDULE |
| `CollectionEvent` | `time`, `type`, `priority`, `start_after_collection_ids`, `missing_type` | Can express collection scheduling context and dependencies, not a complete scheduler causal policy |
| `MachineEvent` | `time`, `machine_id`, `type`, `capacity` | Can express timestamped machine capacity, not proof of instantaneous availability for all jobs |
| `InstanceUsage` | `start_time`, `end_time`, `average_usage`, `maximum_usage`, `assigned_memory` | Describes a period-aggregated measurement; the memory limit does NOT guarantee wallclock runtime |
| `EventType` | `SUBMIT`, `SCHEDULE`, `EVICT`, `FINISH`, `UPDATE_PENDING`, `UPDATE_RUNNING` | Distinguishes placement, updates and transitions; event completion is observable only at or after its actual timestamp |
| `MissingType` | `SNAPSHOT_BUT_NO_TRANSITION`, `NO_SNAPSHOT_OR_TRANSITION`, `EXISTS_BUT_NO_CREATION` | Makes data repairs visible; an inferred or synthesized event must not masquerade as an exactly observed causal history |

**What was NOT verified:** no exact field among the eleven
preregistered runtime-limit name alternatives
(`time_limit`, `runtime_limit`, `walltime`, `wall_time`,
`max_runtime`, `max_duration`, `duration_limit`,
`hard_time_limit`, `deadline`, `execution_timeout`,
`runtime_cap`) occurs in the original pinned proto's declared
fields. This is a **negative statement about the specific public
schema and checked name set**, NOT proof that Google's internal
scheduler has no timeouts, no other runtime-limit vocabulary, or
no administrative enforcement controls.

The existence of `InstanceUsage.assigned_memory` does not
satisfy RP-F007's *maximum service duration* assumption.
Therefore **the original Google Borg v3 schema by itself
cannot justify importing RP-F007's finite wait bounds**.

## The two concrete causal-leakage hazards

The publisher's *Google cluster-usage traces v3* technical
document explicitly warns that **SCHEDULE** is placement
and the actual program may begin later. Missing scheduler
transitions can be synthetically reconstructed, sometimes
at subsequent snapshot timestamps. Those are not necessarily
true contemporary observations.

The same technical document describes usage over typically
300-second periods. A period starting at t=0 and ending at
t=300 cannot contribute its final aggregate usage to a
forecast at t=150; this would reveal measurements from
the future. The preregistered independent event tests
use a STRICT `event_time < prediction_origin` policy
and the conservative `usage_end_time < prediction_origin`
policy, rejecting any synthetically reconstructed
event as exact historical truth.

These tests verify that **our proposed feature rule does
not admit clearly future-ending windows or flagged synthetic
events**. They do NOT verify when provider logging systems
actually make events available, whether all rows exist,
whether CPU/memory usage reflects allocated capacity, or
whether the historical source has enough rows to train
or evaluate a predictor.

## Original provider documentation limitations

The official [publisher repository source](https://github.com/google/cluster-data)
describes a very large corpus (about 2.4 TiB compressed)
and README instructions that refer to BigQuery access.
The publisher's separate
[August 10, 2020 update](https://groups.google.com/g/googleclusterdata-discuss/c/WuRDhbI8YzA)
subsequently describes JSON files in cloud-storage buckets.
We cannot use the README's older BigQuery-only wording to
declare all original raw production data inaccessible.

This audit **made no BigQuery queries and downloaded
zero production trace rows**. The finding concerns only the
two small, verifiably pinned original schema/README files.
A successful source-document download is not data-row
availability, and an archived schema is not a reproducible
prediction experiment.

## Result, stop gates and scope

First-run quality checks all passed: publisher byte identity,
strict UTF-8, required event metadata, synthetic missing-event
flags, and exact agreement between separate field/enum readers.
The prespecified outcome
`SCHEMA_EVENT_METADATA_PRESENT_RUNTIME_CAP_UNVERIFIED`
is therefore final for this first audit; a later source
with stronger time-limit records must be evaluated under
a NEW separate protocol, not retroactively called a
passing RP-E012-D01 hard-cap source.

The constructive finding is that an original trace format
includes potentially useful time-stamped scheduling,
resource-request and machine-capacity information, with
important corrections for causal feature engineering.
The simultaneously important negative finding is that
we have **no verified public guarantee for hard running
time caps** in this source.

It would be unsupported to assert a new numerical bound on
real queue delays, a real-world forecast MAE improvement,
a generalized external validation of RP-F007, or any
meaning for the speculative physical scalar
`C=B/(I tau)`.

## Next distinct research question

The logical next empirical step is **raw-event
availability and missingness audit**, not a new loss
comparison. It would require selecting an actually
accessible subset from the original public provider,
pinning exact machine/cell/time IDs and bytes where
feasible, setting an external download/query cost
budget, defining non-leaky event-time release
semantics, measuring reconstructed-event and missing
coverage, and testing whether scheduling/usage rows
can be joined without future leakage. If the corpus
cannot be accessed at reasonable cost, record
`SOURCE_ACCESS_BLOCKED` and stop rather than
substitute a convenient different source.

Only after independent feature availability can
new heldout forecasts be registered. The previous
RP-E010 and RP-E011 original negatives must remain
unchanged.
