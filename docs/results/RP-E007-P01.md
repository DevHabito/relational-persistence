# RP-E007-P01 — Original prospective two-sample backlog forecast

**First-run registered decision: `PASS_TREND_INCREMENT`.**
All 27 new software-service trials passed the source replayer,
and the predeclared two-sample forecast achieved more than
the required 10% improvement over static backlog/(2B).
This is **classical queue-state estimation**, not evidence for
the proposed physical quotient C or any new physical law.

## Predeclared model and leakage controls

Let `B` be the independently calibrated local work
throughput in work units/second and let `q_prev,q_last`
be queue depth plus active worker count at the
last two *observed* instants no later than injector end.
Both timestamps and the capacity come from archived
original instrumentation.

```text
slope = (q_last-q_prev)/(t_last-t_prev)
h = injector_end-t_last
Yhat_static = max(0, q_last/(2*B))
Yhat_trend = max(0, max(0,q_last+slope*h)/(2*B))
```

Both predictors are **unfitted** and have no tunable
parameters. The constant model is secondary and
uses only the 18 new training Y values. The held-out
Y is replayed from injector end and sampled idle
probe events, independently of any predictor. The
two last pre-end samples must be temporally ordered,
less than 150 ms apart, and the last sample must
be no more than 150 ms old at prediction time.

No post-end sample, observed recovery label or
future service state is allowed as a predictor input.
The original E006 data-collection format is reused
**without repurposing its historical data**. It is
not a separately constructed measurement system.

## Evidence classification and limitations

This is a **restricted, prospective software forecasting
success**, showing that pre-end temporal queue samples
can improve a static backlog approximation for the
specific instrument and selected loads/delays.
It is not a new algorithm, a proof of novel relational
dynamics, or physical evidence that
`C=B/(I*tau)` works. In fact RP-E006's own original
preregistered index-only test remained negative;
nothing here overwrites or repairs that result.

This comparison is a single 9-trial held-out
benchmark, not independently sampled physical
replication, an estimate of a population effect,
or a demonstration of cross-service transfer.
Both jobs share the same cloud provider, source
code and engineered queue process.
A two-point linear extrapolation can also fail
when arrivals are nonlinear, samples are stale,
or service behavior changes outside the specified
system. Do not infer that a trend correction is
universally better.

Prior work includes
[Ross, Taimre and Pollett (2007)](https://doi.org/10.1007/s11134-006-9009-2),
who examine queue estimation from sampled
queue lengths. The project's use of an unfitted
two-sample approximation should **not** be claimed
as original queueing mathematics. Lean 4 regression
passing verifies previously formalized mathematical
statements, not the empirical observations in
this new hosted study.

## Permanent audit

[`tests/test_rp_e007_first_run_archive.py`](../../tests/test_rp_e007_first_run_archive.py)
reads the **original source bytes**, compares the
full 221-file SHA-256 manifest, reexecutes the
measurement and two-source-sample forecast
audits **without rerunning any trial**, and
requires the same positive held-out verdict.
A deliberately corrupted monitor stream must
force STOP instead of a retained positive
classification.

Any new proposed relational state metric should
be specified ahead of new measurements and
evaluated against mature temporal queue/control
models, not just the scalar C or a constant. This
positive result does not close that question.
