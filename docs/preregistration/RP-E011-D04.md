## Frozen scope and row handling

- Obtain **exactly** the named original HTTPS URI, on-host redirects only,
  maximum 150,000,000 bytes. Record HTTP status, exact URL, full SHA-256
  and count. If source bytes or length differ, STOP and **do not parse**.
- Decode strict UTF-8, ignore only blank/comment lines, and parse all
  noncomment 22-field records using `shlex.split`. Independently re-run
  the existing D02 complete source/profile parser. No "fix" of IDs.
- Admit **one and only one known exception** for the NEW D04 prospective
  population: *physical line 1 / data ordinal 1 / integer job ID 0*,
  a known inconsistency with the SWF field-1 positive counter convention.
  Preserve the raw row in the source count, exclude it only from D04's
  proposed later target population, and report exclusion count **1**.
  This handling was selected **after D02/D03 findings**, and cannot be
  presented as blind. Any other invalid/duplicate job ID -> STOP.
- Candidate population after this exception: only positive-ID jobs with
  finite, nonnegative submission time, wait time and runtime, positive
  allocated and requested processor counts, and genuine nonempty
  documented queue name. **No filtering by completion status, queue,
  measured waiting-time magnitude, processor group, or prediction error**.
  A recorded wait implies an observed start in this archived population;
  missing/not-started jobs are inherently absent and selection bias is
  a limitation.
- Study variables for this audit: submit seconds (SWF field 2),
  wait seconds (field 3), allocated processors (5), requested processors
  (8), status (11), and extended queue-name field 20. Do not use
  user/group identifiers, qsub contents, node names or future
  runtime as forecasting features.
- For each included row, define observed start `s = submit + wait`
  using **exact Decimal arithmetic**, require finite `s >= submit`.
  Compute only aggregate row/queue/time-coverage metadata; **no waits
  histogram or target-score distribution**. Do not generate any predictions.

## Fixed prospective diagnostic/holdout split and feasibility gate

Calculate `t_min` and `t_max` from the positive-ID candidate population.
The fixed chronological cutoff is
`T = t_min + 7*(t_max-t_min)/10` in exact decimal seconds.
The diagnostic set has `submit < T`, heldout has `submit >= T`.
Tied submissions remain on the same side of T; no random mixing.
Stable ordering for any later analysis must be by
`(submit_seconds, job_id)`, NOT original file row order.
Count original-file adjacent submission-order inversions and ties,
but **do not** exclude or reorder rows secretly if original file
order differs from the SWF convention.

`TEMPORAL_SOURCE_FEASIBLE` iff all source integrity and original
D02/D03 profile checks pass, the sole exceptional ID is EXACTLY
where D03 found it, all other candidate rows have valid derived
start, and the following **predeclared feasibility conditions** hold:

1. At least **1,000** positive-ID eligible targets on EACH side
   of T.
2. At least **two distinct queue labels** occur on BOTH sides
   with **>=100 targets in each side for each such label**.
3. Every one of the original 472,399 otherwise eligible rows
   is included in exactly one split (no other exclusions).
4. Two independently coded count methods agree on the total
   candidates and both split counts (streaming classification
   versus sorted key partition).

These are only minimum coverage requirements. They do not mean that
statistical units are independent or sufficient for an effect size.
If the official source is unavailable, classify `SOURCE_ACCESS_BLOCKED`.
If bytes or SHA differ, `SOURCE_SHA_MISMATCH`.
If source/independent parsing or original D02-D03 metadata disagree,
`SOURCE_SCHEMA_DISAGREEMENT`. If a valid original source fails fixed
cohort/temporal gates, classify `TEMPORAL_SOURCE_INFEASIBLE`.
Unexpected invalid/nonfinite text is `SOURCE_SCHEMA_DISAGREEMENT`.
All outcomes are final for the **first** D04 run, archived unchanged.

## Causal feasibility and future limitations

Any later P01 model must be separately preregistered, without looking
at its heldout scores, and must enforce strict event-time knowledge:
arrivals with `submit < t` and starts with `start < t` are visible
at prediction origin `t`; a job's eventual wait, runtime, final
status, allocated processors or future actual start are **not**
known at its submission. For tied jobs at time t, no same-time
arrivals or starts may enter the earlier snapshot. Any
training/history wait label may be used only after that job
actually starts, under a declared sequential observational
evaluation. Historical queue-specific and requested-resource
controls must be included. The 13 known queue names provide a
possibility, not proof of causal FIFO dynamics.

D04 computes **no target MAE, no model coefficients, no predictions,
no throughput/persistence scalar C and no new Lean theorem**.
If later hypothesis fails, the negative must be archived. Do not
replace this source or remove an unfavorable queue after observation.
Third-party bulk row data must not be committed to Git; only
metadata, counts, first-run SHA and source acknowledgment.
