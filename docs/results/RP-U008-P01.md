# RP-U008-P01 — Externally recorded gateway and HTTP recovery can differ by one sampling epoch

**Original result, 17 November 2026: RP_U008_TWO_OR_MORE_POSITIVE_HTTP_LAGS_OBSERVED.**

This is an observational audit, not a new outage discovery, intervention experiment, independent hardware measurement, or evidence of a physical or biological persistence law. The source publisher's dataset card already identified the four outages before this study was registered. The registered contribution is a small, reproducible RAW-record cross-protocol comparison with explicit limits.

## Why we moved to external evidence

The previous RP-U007 trial found no confirmed added predictive value from one live work-state measurement beyond accepted workload and calibrated service capacity in a single-host software experiment. RP-U008 deliberately does not extend those artificial queues. It examines a real residential network dataset collected by a separate publisher, with different measured service modalities, but does not claim to explain the physical cause of outages.

Alexander Ezharjan's LocalNet-Dynamics, version 1.0.0 (2026), DOI https://doi.org/10.57967/hf/10841, records gateway and external ICMP, TCP connections, DNS and HTTP results from **one Windows workstation** over approximately 19 days at a nominal 30-second interval. These are distinct protocols recorded by **one collector**. The dataset does not provide independently observed physical repairs or a certified intervention log.

## Frozen endpoint definitions

A raw DOWN row requires ten remote ICMP packets sent with zero received, remote packet loss 100%, and local gateway packet loss 100%. A candidate incident has at least three contiguous DOWN rows with no adjacent timestamp gap greater than 75 seconds. Two independently written selectors matched every candidate. All **four** qualifying events had complete five-row pre-windows and ten-row post-windows; none was excluded or right-censored.

The gateway recovery observation is the **second** of two consecutive post-outage rows in which a local gateway ping received at least one response and had a valid measured gateway RTT. A separate HTTP functional success requires an HTTP status 200–399 and a positive finite response time; the secondary quality endpoint also requires response time at most 1,000 ms. The second of two consecutive post-outage successes defines each recovery index. **One row is an approximately 30-second sampling epoch**, not an exact probe or repair timestamp.

## Complete four-event original result

All source event timestamps below are UTC, not local US Eastern time.

| First DOWN source timestamp (UTC) | Down rows | Gateway pair second post-row | HTTP pair second post-row | HTTP-quality pair second post-row | HTTP versus gateway lag |
|---|---:|---:|---:|---:|---|
| 2026-09-21 17:03:22 | 4 | 2 | 2 | 2 | 0 rows |
| 2026-09-24 11:10:56 | 5 | 2 | 2 | 3 | 0 rows |
| 2026-09-26 17:11:29 | 5 | 2 | 3 | 3 | +1 row (25 seconds between row timestamps) |
| 2026-10-06 06:51:09 | 4 | 2 | 3 | 3 | +1 row (32 seconds between row timestamps) |

The **preregistered descriptive threshold** was reached: **two of four** events had HTTP recovery at a later source row than gateway recovery. The other two had no resolvable HTTP lag. For the stricter under-one-second HTTP quality endpoint, **three of four** events showed a one-row lag. No p-value or population effect is justified by these four preidentified, same-site events.

Original row-level evidence illustrates why the endpoints are distinct. September 21 recovered simultaneously at this source resolution. On September 24, the first post-outage HTTP request succeeded with status 200 but took **3,133.706 ms**; thus the quality endpoint recovered one source row later even though HTTP availability recovered alongside the gateway. On September 26, the first post-outage source row had gateway success but **no HTTP result**, with 40% loss on remote ping; TCP connected but DNS did not return a valid result. On October 6, the first post-outage row again had a gateway reply but **no HTTP, TCP or DNS result**, while remote ping still lost 50%. HTTP later returned on two consecutive source rows. These are recorded associations, not established causal fault paths.

## What cannot be concluded

A gateway ICMP reply after the outage does **not** prove a repaired edge, restored routing topology or physical intervention time. A missing HTTP reply can reflect DNS, transport, remote service or measurement scheduling, as well as actual connectivity. The gateway and HTTP observations come from a **single collector** sampling different endpoints, not independent time-synchronized hardware. The row timestamp labels a measurement epoch; it does not timestamp each protocol's own response. Consequently, the observed **25- and 32-second differences between source row timestamps are not actual measured causal recovery delays**.

The original publisher had already described the four outages, and the author's report discusses response-latency tails. Our result has no priority as an outage discovery, no natural population sampling, and no independent physical outcome validation. It neither proves relational persistence as a theory nor establishes a neuronal, clinical, ecological or fundamental-physics mechanism.

## Where the research genuinely advances

We now have an authenticated **external, non-simulated**, multi-protocol audit showing that a gateway reachability indicator and a basic HTTP functional indicator need not return in the same source epoch in every event. This is a small **measurement-definition and feasibility result**: it makes explicit the observational distinction between a connectivity proxy, HTTP response and HTTP latency quality. The next substantially more discriminating experiment requires more incidents, independently instrumented and separately timestamped physical/control-plane and service-level observations, and a stronger predictor conditioned on existing outage and demand information. Do not describe this n=4 exercise as confirmatory inference.
